# 同源项目文档合并（需求文档 + 设计文档）

触发：把两个同源/分支关系的项目（同产品的领域版与通用版，或重构前后的两份仓库）的多份文档，
合并成一份统一的需求文档与一份统一的设计文档。

## 零、先判定两个项目是什么关系

**不要凭文档标题或 README 自称来猜。** 三步实测：

```bash
# 1. 逐字节对比同名文档：md5 相同 ⇒ 同源复制，看谁在多出的部分上更新
md5 -q A/docs/01-xxx.md B/docs/01-xxx.md
diff A/docs/01-xxx.md B/docs/01-xxx.md | head -80

# 2. 代码模块清单 diff
comm -3 <(ls A/app/*/ | sort) <(ls B/app/*/ | sort)

# 3. 代码行数：分支通常单调增长
wc -l $(find A/app -name '*.py') | tail -1
wc -l $(find B/app -name '*.py') | tail -1
```

| 关系 | 判据 | 合并口径 |
|---|---|---|
| **分支**（B 是 A 的延续） | 底层文档逐字节相同 + 模块单向增加 + 行数增长 | 主线取较新的一支，**领域需求取旧的一支** |
| 平行（各做各的） | 同名文档内容不同结构 | 需求取并集，冲突项单列 |
| 上下游（一个是另一个的依赖） | 模块无重叠 | 分别成文，不合并 |

⚠ **一定要找「反向增量」**：较新的一支常常漏了旧支的某个修复（新增模块、文档多出的一节）。
`diff` 双向跑，不要只看 `A → B`。这类遗漏要显式写进文档。

## 一、开工前必做的四件事

1. **列出全部源文档清单并全部通读**。不要只读 README 和「方案」就动笔——
   真正的设计判断藏在「实施进展」「踩坑」「已知限制」这些小节里。
2. **定位「被引用但不存在的原件」**。文档里常有「详见 `设计方案/01-需求分析与系统设计.md`」，
   而该文件可能根本不在仓库里。全仓检索确认后**显式记录**，标为「二手引用」。
   **不补、不猜、不留白当成有。**
3. **提取工程事实作为基准**（这些数字后面会反复用到）：
   ```bash
   grep -oE '@app\.(get|post|put|delete|patch)\("[^"]+"' app/*/api.py | wc -l   # 端点数
   grep -c 'CREATE TABLE IF NOT EXISTS' app/*/schema_pg.py                      # 表数
   grep -oE 'add_parser\("[^"]+"' app/*/cli.py | wc -l                          # CLI 子命令数
   ```
4. **记录「文档与配置不一致」**。至少查：默认值在 compose / 代码 / `.env.example` 三处是否一致、
   容器计数与清单是否对得上、CI 脚本的前置检查是否要求了已废弃的容器。
   在文档开头集中列表，并声明「**以代码为准**」。

## 二、需求文档的写法

- **统一编号**：`FR-xxx` / `NFR-xx`，逐条标注**口径来源**（来自哪一期/哪个文档）与**落地状态**。
- **保留演进链，不要抹平**。需求会被推翻，而「为什么推翻」比「现在是什么」更有价值。
  用「A → B」写清推翻前后的口径与理由。
  典型：六角色 → 两维角色；标签模型 → 库成员模型；一文档一库 → 跨库授权；自由文本部门 → 受控实体。
- **差异单出附录**：领域版与通用版的差异（语料、权限模型、技术底座、领域独有风险）
  **不要合并成一份「都适用」的模糊表述**，单开附录逐项对照，并给出「应当补做的事」。
- **边界与「明确不做」独立成章**：含合规红线、被评估后放弃的方案及其结论理由。
- **验收标准要能复述**：门槛 + 编号验收项（AC-x）+ 从踩坑里提炼的方法论。

## 三、设计文档的写法

建议骨架（按依赖顺序，不按重要性）：

```
〇 阅读须知（设计基线 / 历史层保留 / 以代码为准 / 不一致清单）
一 总体架构（设计原则 → 容器拓扑 ASCII 图 → 为什么这样分 → 端口与启动依赖 → 数据流）
二 技术选型（选型总表 → 每处偏离的理由 → 底座更换的 POC 结论）
三 数据层（表清单 → 多租户模型 → RLS 策略 → 向量层 → 关键词层 → 方言兼容层 → 结构迁移）
四 内核设计（角色 → 命名空间/标签模型 → 铁律 → 各级实现 → 错误处理与「静默失败」防线）
五 模块设计（模块总览表 → 窄接口契约 → CLI → 可观测性）
六 接口设计（端点清单按域分组 → 接口约束 → 边界语义）
七 前端设计（技术形态 → 页面清单 → 硬性约束 → 交互细节 → 文案要求）
八 部署与运维（目录 → 一键初始化 → 切换方案 → 参数默认值分组表 → 备份 → 环境风险）
九 验证与验收（几道门 → 退出码分层 → 断言矩阵 → 方法论）
十 关键设计决策与踩坑教训  ← 复用价值最高
十一 已知限制（按子系统分组）+ 待决策清单
附录（依赖版本 / 模块索引 / 脚本索引 / 表索引）
```

**第十章是重点**，好的组织方式是**按主题**而不是按时间：

1. **静默失败谱系**——「错误被翻译成正常结果」的所有实例，逐个给：位置 / 症状 / 修法。
2. **跨模块隐含耦合**——不会在 import 图上体现、只在「改一处漏一处」时爆炸的耦合对，
   做成两列表：耦合对 / 为什么危险与处置。
3. **「机制全绿、界面点不动」这一族**——共同特征是某层用了另一套名字/判据，症状离原因很远。
4. **其它坑按主题分组**：构建与依赖 / 配置与编排 / 环境与脚本 / 前端 / 数据与模型 / 验收脚本。

## 四、写作纪律

- **分段写入**。单次写入超过约 40 KB 会触发工具参数序列化失败
  （`Parameter "file_path" expected string, but received undefined`）。
  做法：先写第一段，之后每次用编辑工具把**文件末尾一小段唯一文本**作锚点，
  替换为「该文本 + 新章节」。每段控制在 10–15 KB。
- **表格优先于段落**。这类文档的读者是检索式的，不是通读式的。
- **每个结论都要能追到源**。写「32 条断言」就真去数一遍；写「69 个端点」就真去 grep 一遍。
  文档里出现未经核实的数字，等于把一份参考文档变成一份负债。
- **标 ⚠ 的条目要克制**：只给「知道就好、但要防误判」的内容（历史遗留、窄边界、正确但反直觉的行为）。
