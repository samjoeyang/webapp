# 家庭网络诊断：方法论与指标解读

本文件是「家庭网络诊断专家」技能的领域知识核心。它把 `assets/network-check.html`（浏览器端自检工具）的检测原理、阈值口径、评分模型与解读逻辑完整拆解为可被专家复用的判断依据。无论是解读工具输出，还是直接回答用户的网络问题，都以此为准。

## 一、检测项总览（14 项）

| # | 检测项 | 测量对象 | 主要手段 |
|---|--------|----------|----------|
| 1 | 延迟与抖动 | 到多个远端节点的 RTT、抖动、丢包 | 多节点并行 `fetch` 探测（no-cors），每节点采样 20 轮 |
| 2 | 网速 | 下行 / 上行带宽 | Cloudflare 测速节点（`__down` / `__up`，CORS 开放） |
| 3 | DNS 解析 | 域名解析 + 建连耗时 | 「首次解析（no-store）+ 二次缓存（force-cache）」差值估算 |
| 4 | IPv6 支持 | 是否经 IPv6 出网 | `ipv4.icanhazip.com` vs `ipv6.icanhazip.com` |
| 5 | 饱和 / Bufferbloat | 满载时延迟增量 | 边下载边测延迟（读取下载流的同时并行探测） |
| 6 | WebRTC 隐私 / NAT | 浏览器暴露的真实 IP 与 NAT 类型 | STUN 收集候选地址（Google / Cloudflare） |
| 7 | 本地服务暴露扫描 | 本机 127.0.0.1 常见端口 | 仅探测本机，安全 |
| 8 | 安全 / 加密姿态 | HTTPS / DoH / 混合内容 | `isSecureContext` + 资源条目 + DoH 探测 |
| 9 | 连接基线 | 浏览器报告的连接类型 / 下行 / RTT | `navigator.connection`（可能不存在） |
| 10 | 综合评分 | 0–100 健康分 | 由上述指标加权扣减 |
| 11 | 智能诊断 | 分级结论 + 修复建议 | 规则引擎（见下文） |

## 二、核心指标口径

### 2.1 延迟 / 抖动 / 丢包（单节点）

- **平均延迟 (avg)**：有效采样（rtt < 2500ms）的算术平均。
- **抖动 (jitter)**：相邻两次有效 RTT 之差的绝对值的平均（mean abs diff）。衡量「波动剧烈程度」，不是标准差。
- **丢包 (loss)**：`(总采样 − 有效采样) / 总采样 × 100%`。单次超时即算一次丢包。
- 判定告警：抖动 > 25ms 视为异常（`JITTER_THRESH=25`）。

### 2.2 同步抖动（关键根因信号）

工具最强的根因定位能力在这里：

- 对每个采样轮，统计「该轮内有多少个节点同时尖峰」——尖峰定义为 `rtt ≥ 2500ms` 或 `rtt > 该节点基线 + 40ms`。
- 若**同一轮内有 ≥ 2 个节点同时尖峰**，记为一次「同步尖峰轮」。
- `同步比例 = 同步尖峰轮数 / 总轮数`。

| 同步比例 | 解读 | 根因指向 |
|----------|------|----------|
| > 25% | 多节点在同一时刻一起尖峰 → **瓶颈在本地路径**（路由器 CPU/NAT 或 WiFi 调度） | 本地 / 路由器 |
| 0%–25% | 节点尖峰不同步，多为各服务器自身波动 | 远端 / 各自波动 |
| 0% | 平稳 | 无明显同步抖动 |

> 原理：若瓶颈在远端服务器，各服务器不会在同一瞬间一起变差；只有本地（路由器/NAT/WiFi）出问题，才会让所有出向连接同时恶化。

### 2.3 网速分级

| 实测下行 | 评级 |
|----------|------|
| ≥ 30 Mbps | 正常 |
| 10–30 Mbps | 偏低（扣 5 分） |
| < 10 Mbps | 明显偏低（扣 15 分） |

> Cloudflare 测速节点在部分网络下不可达，会显示「不可用」——属正常，不代表网速真差，需换测速源或本地测速复核。

### 2.3.1 测速有效性校验（反常校验，重要）

单点测速极易被「坏节点」误导——曾有真实案例：浏览器测速下载 4.89 Mbps、上传却 25 Mbps（下载低于上传在物理上反常），而改用路由器官方 App 测速实得下载 355 Mbps。即「AI 拿着一把坏尺子量东西，量出来的结论全歪」。

工具在 `analyze()` 内置反常校验：**当实测下行 < 上行（且上行有效）时**，判定为「测速节点/链路异常」（节点故障、被限速到单线程等），而非真实网速，并提示用「路由器官方 App 自带测速」或运营商测速页（电信/联通/移动宽带管家）复核，以权威源为准。

> 验收原则：任何「测速远低于套餐」「下载 < 上传」「数据明显不合常理」的结论，都**先怀疑测量本身**，用路由器/运营商权威源交叉验证后再下结论，绝不拿单一测速网站的数字当铁证。

### 2.3.2 双频合一识别（高套餐低速的头号嫌疑）

「双频合一 / _band steering_」让 2.4G 与 5G 共用一个 WiFi 名，设备常被默认连到覆盖广但速率低的 2.4G，导致办了 500M 宽带却只跑几十兆。

**主动问诊（出现「高套餐低速 / 手机视频卡」时必问）**：
1. 宽带签约速率多少兆？
2. 路由器什么型号？
3. WiFi 名有几个（是否双频合一）？设备当前连的是 2.4G 还是 5G（手机 WiFi 详情里看频段/信道）？

**判定规则**：签约速率高（如 ≥200M）但实测下行低，且「单 SSID + 设备连 2.4G」→ 疑似双频合一限速。首选动作：进路由器后台关闭双频合一，将 2.4G/5G 分成两个名字，近处设备手动连 5G 后再验收。

> 该判定依赖用户自报的频段/SSID 信息，工具无法远程读取设备所连频段；Agent 应主动问诊而非臆测。

### 2.4 DNS 分级（解析 + 建连耗时估算）

| 耗时 | 评级 |
|------|------|
| < 60ms | 正常 |
| 60–150ms | 偏慢 |
| ≥ 150ms | 慢 |

### 2.5 Bufferbloat 评级（延迟增量 Δ = 满载 − 空闲）

| Δ 增量 | 评级 | 含义 |
|--------|------|------|
| < 30ms | A | 优秀，无明显 bufferbloat |
| 30–60ms | B | 良好，轻微增加 |
| 60–120ms | C | 一般，存在 bufferbloat 迹象（扣 5 分） |
| 120–200ms | D | 较差，bufferbloat 明显（扣 10 分） |
| ≥ 200ms | F | 严重，典型 bufferbloat（扣 15 分） |

### 2.6 IPv6

- 能经 `ipv6.icanhazip.com` 获取到地址 → 已支持 IPv6（提示可优先 IPv6 缓解 IPv4 抖动）。
- 获取不到 → 仅 IPv4，属可选优化项，不扣健康分，仅作提示。

### 2.7 本地端口危险等级

扫描端口：`22/80/443/3306/5432/6379/9200/27017/3389/5900/8888/3000/5000/8000`。
危险服务（高风险暴露）：`3306(MySQL) 5432(PostgreSQL) 6379(Redis) 9200(Elasticsearch) 27017(MongoDB) 3389(RDP) 5900(VNC) 8888(Jupyter)`。

> ⚠️ 若页面以 **HTTPS** 打开，浏览器会**禁止访问 `http://127.0.0.1`**，导致本地扫描/Clash 本地检测整项为空。需用 `http://` 或 `file://` 协议打开本页才能正常探测。

### 2.8 WebRTC / NAT

- 收集到**非内网 IP** 即视为「暴露真实公网 IP」。
- NAT 类型：用两个不同 STUN 服务器取 `srflx` 反射地址，两者相同 → 锥形 NAT（较宽松）；不同 → 对称型 NAT（最严格）；取不到 → 被防火墙拦截。

### 2.9 Clash 本地安全

探测 `http://<host>:<port>/version` 与 `/proxies`：

| 结果 | 判定 |
|------|------|
| `/proxies` 可无密钥读取 | 🔴 高危：控制端口开放且无 secret，本地任意网页可读你的代理节点与连接 |
| `/proxies` 返回 401/403 | 🟢 已保护：访问敏感接口需 secret 鉴权 |
| 端口可达但敏感接口受限 | 🟠 需注意 |
| 不可达 | 未暴露（可能 Clash 没跑，或被 HTTPS 页拦截） |

## 三、综合评分模型（computeScore）

基线 100 分，按顺序扣减（扣完不返负）：

```
score = 100
score -= max(0, 平均延迟 − 30) × 0.4
score -= max(0, 平均抖动 − 10) × 0.8
score -= 丢包率% × 1.5
若 下行<10  → −15；下行 10–30 → −5
若 Bufferbloat F → −15；D → −10；C → −5
若 非 HTTPS 或存在混合内容 → −3
```

健康分区间：≥80 绿、55–79 黄、<55 红。

## 四、智能诊断规则（analyze，按优先级）

下表按代码中 `level=Math.min` 的生效顺序（越靠前越优先把整体定级拉低）：

| 触发条件 | 结论 | 等级 |
|----------|------|------|
| 下行 < 上行（且上行有效） | 测速结果反常（节点/链路异常，非真实网速） | 🔴1 |
| 丢包率 > 2% | 网络异常（丢包） | 🔴1 |
| 同步比例 > 25% | 本地/路由器瓶颈（同步抖动） | 🔴1 |
| 抖动 > 25ms | 延迟抖动较大 | 🟠2 |
| 平均延迟 > 80ms | 基础延迟偏高 | 🟠2 |
| 下行 < 10 Mbps | 带宽偏低 | 🟠2 |
| Bufferbloat F/D | Bufferbloat 严重（饱和抖动） | 🔴1 |
| Bufferbloat C | 存在 Bufferbloat 迹象 | 🟠2 |
| 本机开放危险端口 | 本机暴露危险服务 | 🔴1 |
| 非 HTTPS / 混合内容 | 连接安全姿态不足 | 🟠2 |
| 未启用 IPv6 | 未启用 IPv6（提示） | 🟢3 |
| WebRTC 暴露公网 IP | 真实 IP 可见 | 🟢3 |
| 以上皆无 | 各项指标正常 | 🟢3 |

> 🔴=lv1（高危，需立即处置）｜🟠=lv2（中等，建议优化）｜🟢=lv3（信息/可选）。

## 五、解读输出模板（专家建议时复用）

给用户结论时，按「**判定 → 根因 → 证据 → 处置**」四段给：

1. **判定**：一句话结论（如「本地/路由器瓶颈导致的同步抖动」）。
2. **根因**：指出瓶颈落在哪一层（本机 / 路由器 / 运营商 / 远端）。
3. **证据**：引用具体数字（同步比例 X%、抖动 Yms、Bufferbloat 评级 Z、下行 W Mbps）。
4. **处置**：给出分层可执行的修复步骤（见《处置手册》）。

不要臆造工具没有测到的数据；若某项显示「不可用/未检测」，明确说明其不代表异常，仅在条件满足时才能下结论。
